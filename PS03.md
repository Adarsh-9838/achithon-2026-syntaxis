## Domain

Machine Learning, Model Adaptation, Error Analysis, and Evaluation Engineering


## Problem Statement

A machine-learning classifier may perform well overall while repeatedly making mistakes on a particular category. Improving that weakness through additional training or fine-tuning can affect other categories, creating new errors or reducing previously satisfactory performance.

For example, a support-ticket classifier might frequently confuse “Account Access” requests with “General Enquiries.” Further training on account-access examples could improve that category while making the model incorrectly assign unrelated requests to it.

Develop a targeted model-repair pipeline that identifies a specific weakness in an existing lightweight classifier, applies a justified adaptation strategy, and evaluates whether the resulting improvement introduces unacceptable performance losses elsewhere.

In this challenge, a regression means a decline in previously measured classification performance. The system must produce an evidence-based decision: accept the repaired model or retain the original model, according to evaluation rules established before final testing.

### Required Scope and Workflow

The pipeline must implement a structured, reproducible 7-step repair and evaluation process:

- 1\. Load and validate the model and datasets: Use one classification task, one lightweight baseline model, and separate train/val/test splits. Preprocessing fitted from data must use the training split only.
- 2\. Identify a repair target: Analyze baseline validation performance. Select one weak category and describe recurring errors using misclassified examples and a confusion matrix.
- 3\. Define the acceptance policy: Specify minimum required improvement for the target category and maximum acceptable decline for overall and non-target performance before testing.
- 4\. Apply a repair strategy: Implement a training-based adaptation (targeted fine-tuning, class-weighted loss, data augmentation, or balanced representative mixtures). Keep validation and evaluation examples out of repair training.
- 5\. Select final candidate: Compare candidate settings on validation data only. Freeze model checkpoint, preprocessing, and acceptance policy before held-out evaluation.
- 6\. Perform held-out comparison: Evaluate original and repaired models on the identical held-out test split. Report target, overall, and non-target metrics with sample counts.
- 7\. Generate an explicit decision: Accept the repaired model only when it meets every condition; otherwise reject it and report which conditions failed. Preserve both versions.

### Evaluation Metrics & Illustrative Policy

Key metrics: Target-category F1 (targeted improvement), Macro F1 (overall preservation), Non-target category F1 (granular regression detection), and Confusion Matrix with Changed Predictions (error analysis).

Illustrative Acceptance Policy: Target-category F1 must increase by at least 3 percentage points; overall macro F1 may decrease by no more than 1 percentage point; no individual non-target category may lose more than 2 percentage points of F1.

For a manageable 24-hour implementation, focus on one small dataset, one baseline model, one target category, and at least one repair strategy.

## Key Deliverable

A working experiment dashboard supported by executable training and evaluation code. The dashboard must include:

- Dataset overview: Split sizes, category distribution, sample identifiers, and validation findings.
- Baseline analysis: Validation metrics, confusion matrix, representative errors, and the selected repair target.
- Repair configuration: Adaptation method, relevant hyperparameters, training budget, and acceptance thresholds.
- Model comparison: Side-by-side baseline and repaired-model results, including absolute metric changes for every category.
- Changed-prediction analysis: Examples corrected by the repair and examples that became incorrect after repair.
- Acceptance decision: A clear accepted or rejected result, with the individual condition responsible for each pass or failure.

The submission must also provide: original and repaired model checkpoints with preprocessing info; saved experiment configuration (fingerprints, splits, seeds); evaluation report and prediction exports; a README explaining reproduction; and tests covering acceptance-rule boundaries and metric calculations.

Optional Advanced Extension: Compare multiple repair strategies, repeat experiments across several seeds, or estimate uncertainty around metric differences.

### Expected Outcome

An auditable pipeline showing whether a targeted model adaptation produces a useful improvement without exceeding its predefined regression limits.

A successful submission must explain what improved, what deteriorated, and why the final decision follows from the declared rules. A correctly rejected repair remains a valid experimental result when the pipeline and evaluation are sound.

Acceptance demonstrates compliance with the chosen benchmark and policy; it does not establish performance beyond the evaluated data.
